# YubiKey-Backed Zero-Knowledge Authentication Protocol

## 1. System Requirements
* **Hardware Token:** Standard off-the-shelf YubiKey utilizing the PIV applet.
* **Server Resistance to Offline Compromise:** The server must not store the Data Encryption Key (DEK) in plaintext or hold any static key capable of decrypting the stored DEK.
* **Ephemeral Client Trust:** The client laptop is permitted to hold secrets (the DEK and derived keys) temporarily in volatile memory (RAM), but must not store them on disk.
* **No Plaintext Transmission:** The DEK must never be transmitted over the network in plaintext.
* **Hardware-Only Client Asymmetry:** The client software must not possess or manage its own asymmetric keypair. It strictly relies on the YubiKey's ECC pairs for all asymmetric operations.
* **Anti-Replay & Hardware Proof:** All unlock requests must be bound to a fresh server challenge (Nonce) and mathematically prove the physical presence of the YubiKey during the exact session by relying on hardware-backed ECDH operations bound to the session nonces via AES-SIV AEAD.

---

## 2. Cryptographic State & Initialization

### 2.1 Entity Key Material
* **Server:** 
  * Static ECC Keypair: $(K_{S\_priv}, K_{S\_pub})$
  * Knows YubiKey Public Key: $K_{yk\_ecdh\_pub}$ (Slot 9D)
* **Client:** 
  * Knows Server Public Key: $K_{S\_pub}$
* **YubiKey (PIV Applet):**
  * Slot 9D (Key Management): ECC Keypair $(K_{yk\_ecdh\_priv}, K_{yk\_ecdh\_pub})$ configured for ECDH.

### 2.2 Phase A: Server-Side Offline Protection (Setup / Key Rotation)
*Objective: Encrypt the DEK such that only the physical YubiKey can participate in its decryption, utilizing ECIES to strip the server of decryption privileges.*

1. Server generates the Data Encryption Key ($DEK$).
2. Server generates a one-time ephemeral ECC keypair: $(K_{E\_priv}, K_{E\_pub})$.
3. Server computes the offline shared secret: 
   $$SharedSecret_{offline} = \text{ECDH}(K_{E\_priv}, K_{yk\_ecdh\_pub})$$
4. Server derives the wrapping key via HKDF: 
   $$K_{offline} = \text{HKDF}(SharedSecret_{offline}, \text{salt=None})$$
5. Server encrypts the DEK using AES-SIV (with a static all-zero nonce, since the ephemeral key guarantees freshness): 
   $$C_{YK} = \text{AES-SIV-Encrypt}(K_{offline}, \text{nonce=}0, \text{msg=}DEK)$$
6. Server **permanently destroys** $K_{E\_priv}$ and the plaintext $DEK$. 
7. Server stores $C_{YK}$ and $K_{E\_pub}$.

## 3. The Execution Flow (Unlock Algorithm)

### 3.1 Phase B: Client Hardware Unwrapping
*Objective: The client securely retrieves the DEK into volatile memory.*

1. **Challenge:** Server generates a cryptographically secure Nonce $N_S$ (Server Nonce).
2. **Delivery:** Server transmits $N_S$, $C_{YK}$, $K_{E\_pub}$, and $K_{S\_pub}$ to the Client.
3. **Hardware ECDH:** Client passes $K_{E\_pub}$ to YubiKey Slot `9D`.
4. **Token Response:** YubiKey computes $SharedSecret_{offline} = \text{ECDH}(K_{yk\_ecdh\_priv}, K_{E\_pub})$ and returns it to the Client.
5. **Decryption:** Client derives $K_{offline} = \text{HKDF}(SharedSecret_{offline})$ and decrypts $C_{YK}$ using AES-SIV with an all-zero nonce to hold the raw $DEK$ in RAM.

### 3.2 Phase C: Hardware-Backed Transport Wrapping
*Objective: The client establishes a mutually authenticated tunnel to the server and proves physical token presence.*

1. **Client Nonce:** Client generates a cryptographically secure Nonce $N_C$ (Client Nonce).
2. **Tunnel ECDH:** Client passes Server's static key $K_{S\_pub}$ to YubiKey Slot `9D`.
3. **Token Response:** YubiKey computes $SharedSecret_{transport} = \text{ECDH}(K_{yk\_ecdh\_priv}, K_{S\_pub})$ and returns it to the Client.
4. **Key Derivation:** Client uses HKDF with the Client Nonce as salt to bind the session key: 
   $$K_{transport} = \text{HKDF}(SharedSecret_{transport}, \text{salt=}N_C)$$
5. **Payload Wrapping:** Client encrypts the $DEK$, using $N_C$ as the AES-SIV nonce, and the Server Nonce $N_S$ as Associated Data (AAD) to prevent ciphertext detachment and replay attacks:
   $$Ciphertext = \text{AES-SIV-Encrypt}(K_{transport}, \text{nonce=}N_C, \text{msg=}DEK, \text{AAD=}N_S)$$
6. **Cleanup:** Client wipes $DEK$, Shared Secrets, and Keys from RAM.
7. **Transmission:** Client transmits $Ciphertext$ and $N_C$ to the Server.

### 3.3 Phase D: Server Verification and Unlock
*Objective: The server validates the session, the hardware presence, and mounts the keystore.*

1. **Tunnel ECDH:** Server computes the mirror shared secret:
   $$SharedSecret_{transport} = \text{ECDH}(K_{S\_priv}, K_{yk\_ecdh\_pub})$$
2. **Key Derivation:** Server derives $K_{transport} = \text{HKDF}(SharedSecret_{transport}, \text{salt=}N_C)$.
3. **Decryption & Session Validation:** Server attempts AES-SIV decryption using $N_C$ as the nonce and $N_S$ as the expected AAD. 
   * *Failure condition: If the AES-SIV tag is invalid or the expected AAD ($N_S$) does not match, the decryption fails, indicating the payload was tampered with, replayed, or generated by an entity without the correct hardware-backed shared secret.*
4. **Nonce Invalidation:** Server marks $N_S$ as consumed to prevent replay attacks.
5. **Unlock:** If all validations pass and decryption is successful, the Server extracts the plaintext $DEK$ and uses it to mount the target keystore into memory.
